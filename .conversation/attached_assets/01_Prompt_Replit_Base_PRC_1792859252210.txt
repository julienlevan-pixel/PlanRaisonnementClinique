# Prompt 1 — Replit : construire la base fonctionnelle de PRC Pharmacie

Construis une première version fonctionnelle, en français, de « PRC Pharmacie », une application de Plans de raisonnement clinique. Elle doit permettre le parcours complet : créer un cas → faire répondre un panel d’experts → générer et valider son corrigé → faire répondre les étudiants → restituer et publier leurs résultats.

La cible finale est une classe d’environ 250 à 300 étudiants. Prépare une base compatible avec cet usage ; sa capacité effective sera mesurée lors de l’étape Codex.

Cette étape doit produire une base compacte et réellement utilisable. Les améliorations visuelles, la démonstration clinique complète et les tests de charge seront réalisés ensuite avec Codex, depuis GitHub. Travaille par petits jalons et vérifie chaque parcours. Si ce projet contient déjà du code ou des données utiles, inspecte-les et réutilise-les plutôt que reconstruire les parties conformes.

## Comprendre le fonctionnement pédagogique avant de construire

L’objectif est d’entraîner le raisonnement clinique : devant un même cas, identifier l’hypothèse diagnostique la plus probable, proposer une hypothèse alternative et justifier chacune par les observations les plus discriminantes.

Les quelque 20 données cliniques constituent les informations d’un seul cas : symptômes, antécédents, traitements, résultats d’examen, etc. Le participant les consulte, choisit deux diagnostics distincts parmi les possibilités préparées par le professeur, puis sélectionne les données qui soutiennent ou affaiblissent chaque hypothèse. Il ne classe pas nécessairement toutes les données.

Une réponse individuelle comprend donc :
- Une hypothèse principale : le diagnostic jugé le plus probable, accompagné des données retenues et de leur signe.
- Une hypothèse alternative : un autre diagnostic envisagé, accompagné de sa propre sélection et de ses signes.

Le signe porte toujours sur le lien entre une observation et le diagnostic choisi : « + » signifie que l’observation favorise cette hypothèse ; « − » signifie qu’elle la rend moins probable. Une même observation peut être retenue pour les deux hypothèses avec des signes différents. Le panel sélectionne cinq données par hypothèse ; les étudiants peuvent en sélectionner de une à cinq.

Le parcours du professeur suit quatre étapes visibles :
1. **Préparer le PRC** : donner un nom au cas, rédiger le scénario, proposer les diagnostics et saisir les données cliniques. Aucune bonne réponse n’est encore définie.
2. **Recueillir le panel** : inviter les experts, qui remplissent individuellement le questionnaire sans voir les réponses des autres.
3. **Établir le corrigé** : fermer le panel, consulter les distributions de ses réponses, puis valider la référence produite par ces réponses. Cette référence conserve les désaccords et les choix minoritaires ; les règles de pointage sont précisées plus bas.
4. **Animer avec les étudiants** : lancer le même cas avec la référence validée, recueillir leurs réponses, guider la discussion en révélant progressivement les résultats, puis publier les scores individuels.

Le questionnaire des experts et celui des étudiants utilisent le même tableau et la même logique de réponse. Le professeur peut montrer les résultats au panel après sa fermeture. Il peut ensuite réutiliser le PRC et son corrigé validé avec plusieurs groupes d’étudiants : chaque lancement garde ses propres participants et résultats, sans refaire le panel si le contenu clinique reste identique.

## 1. Architecture à respecter dès le départ

Destination finale : Netlify pour l’interface et les fonctions serveur ; Supabase pour PostgreSQL. Replit sert au développement, pas à fournir un service indispensable à la production.

- Interface React + TypeScript + Vite ; une application web responsive simple.
- API TypeScript compatible avec Netlify Functions, sous /api. Utiliser des handlers HTTP courts, indépendants d’un serveur permanent. Isoler la logique métier et l’accès aux données pour les tester.
- En développement Replit, faire fonctionner interface et fonctions ensemble, de préférence via l’émulation Netlify adaptée à Vite ; employer Netlify Dev si nécessaire. Ne pas créer deux implémentations de la logique métier.
- PostgreSQL dans un projet Supabase de développement dès cette étape. Accès SQL paramétré uniquement depuis le serveur ; aucun accès direct du navigateur aux tables métier.
- Prévoir un schéma privé non exposé à la Data API, par exemple prc_private, sans droits pour les rôles publics anon et authenticated. Les droits applicatifs sont vérifiés par l’API.
- Connexions serveur via le pooler Supabase adapté aux fonctions serverless, avec petit pool et prepared statements désactivés en mode transaction. Conserver les identifiants SQL exclusivement côté serveur.
- Toutes les sessions, copies, autorisations et étapes d’animation sont persistées. Aucun état indispensable en mémoire d’un processus ou dans un fichier local.
- Le navigateur appelle l’API sur la même origine ; aucune dépendance à un backend Replit en production.
- Ajouter dès maintenant netlify.toml, le build statique, la configuration des fonctions et les routes nécessaires. La redirection de l’application ne doit pas masquer les routes API.

Fournir des migrations SQL versionnées, une commande explicite pour les appliquer et une initialisation reproductible. Les migrations ne sont pas exécutées à chaque requête ou automatiquement sur la production à chaque build. Utiliser une connexion de migration appropriée, distincte de la connexion d’exécution si nécessaire.

## 2. Accès : comptes créés uniquement par moi

Je suis l’unique administrateur initial. Je crée manuellement le nom d’utilisateur et le mot de passe initial des quelque 10 à 20 enseignants autorisés. Aucun formulaire ou endpoint d’inscription publique. Aucune adresse courriel, identité Replit ou connexion sociale obligatoire.

Prévoir un écran administrateur minimal : créer un enseignant, consulter les comptes, réinitialiser un mot de passe, désactiver ou réactiver un accès. L’administrateur peut aussi créer et animer ses propres PRC. Un enseignant gère uniquement ses propres contenus.

Utiliser une bibliothèque cryptographique éprouvée pour les hachages de mots de passe ; jamais de stockage en clair ou réversible. Sessions opaques avec jetons aléatoires, empreinte conservée en base et cookie HttpOnly, Secure en production, SameSite adapté. Vérifier rôles et propriété côté serveur, protéger les mutations contre les requêtes forgées et limiter les tentatives de connexion avec un mécanisme compatible serverless. Réinitialiser ou désactiver un compte invalide ses sessions. Prévoir le changement du mot de passe initial.

Initialiser mon compte par une commande privée utilisant ADMIN_INITIAL_USERNAME et ADMIN_INITIAL_PASSWORD, sans valeur réelle dans Git. L’initialisation ne doit ni promouvoir le premier visiteur ni réinitialiser un compte existant à chaque lancement. Préserver mon accès de propriétaire si le projet contient déjà des comptes.

Supabase est utilisé ici comme base PostgreSQL. Ne pas remplacer le parcours nom d’utilisateur/mot de passe par une inscription Supabase Auth par courriel. Si une authentification compatible existe déjà, la conserver et documenter son fonctionnement.

Les experts et étudiants participent sans compte enseignant. Leurs accès ne donnent aucun droit de création de PRC ou de gestion des utilisateurs.

## 3. Bibliothèque et création du PRC

Le parcours est centré sur un seul nom de PRC. Depuis « Mes PRC », proposer : modifier, faire répondre le panel, consulter le corrigé, lancer avec les étudiants et voir les résultats. Aucun titre de séance ni numéro de cours obligatoire. Chaque lancement reçoit automatiquement sa date, son identifiant et son code ; les groupes restent séparés.

L’éditeur comprend : nom, scénario, consignes préremplies, liste de diagnostics proposés et données cliniques. Exiger au moins deux diagnostics. Le professeur ne saisit pas de bonne réponse ou de points avant le panel.

La saisie des données est prioritaire : une grande zone où coller une observation par ligne, puis une action pour créer environ 20 observations directement modifiables. Catégorie facultative avec valeur par défaut. Autoriser plus ou moins de 20 données, leur suppression et leur réorganisation. Sauvegarder réellement en base, avec un indicateur d’enregistrement.

Un brouillon incomplet peut être enregistré. Figer le questionnaire utilisé lors d’un lancement. Toute modification clinique ultérieure crée une autre version : elle ne change ni les anciennes copies ni les corrigés déjà utilisés. Les versions restent discrètes dans l’interface.

## 4. Questionnaire commun aux experts et étudiants

Présenter le cas et une seule liste de données en tableau. Deux groupes de colonnes : hypothèse principale et hypothèse alternative. Chaque groupe affiche le diagnostic choisi, les cases de sélection, les signes « En faveur (+) / En défaveur (−) » et son compteur.

- Deux diagnostics obligatoirement distincts, choisis dans la liste du professeur.
- Maximum de cinq données par hypothèse, indépendamment ; une même donnée peut servir aux deux, avec des signes différents.
- Un signe obligatoire par sélection ; pas de sixième choix, dans l’interface et sur le serveur.
- Pour cette base, fixer cinq choix par hypothèse au panel ; autoriser une à cinq données par hypothèse aux étudiants. Les réglages avancés viendront ensuite.
- L’étudiant révise avant confirmation de sa soumission définitive, puis la copie est verrouillée.
- Un changement de diagnostic oblige à revoir les signes de sa justification.
- Les brouillons sont sauvegardés et repris après actualisation. Un brouillon non soumis reste « Non soumis », exclu des statistiques et non noté zéro.

Ne pas envoyer aux participants le corrigé, les points ou les choix d’autrui pendant la collecte. Les masquer visuellement ne suffit pas.

## 5. Panel, corrigé et pointage

Chaque lancement possède un lien, un QR code et un code alphanumérique utilisables. Un code identifie l’activité ; une contribution experte exige une invitation individuelle valide ou une approbation du professeur. Un accès étudiant ne peut pas devenir un accès expert. Le participant reçoit un jeton sécurisé de reprise ; le pseudonyme n’autorise pas la lecture d’une copie existante.

Le panel répond sans référence préalable. Le professeur ferme la collecte, puis peut révéler les résultats aux experts par une action distincte. Aucun résultat collectif avant la fin du panel ; pas de note attribuée aux experts sur leur propre référence.

Générer le corrigé à partir de toutes les copies expertes définitives du lancement retenu, sans mélanger les campagnes. Bloquer la génération sans copie ou sous le minimum positif configuré par le professeur. Conserver les réponses minoritaires et les divergences de signes.

Pour chaque rôle r et diagnostic d, enregistrer l’effectif N_r(d) et, pour chaque donnée c, les nombres de choix + et −. Les non-sélections valent N_r(d) moins ces deux effectifs. Pourcentages diagnostiques sur l’ensemble du panel ; pourcentages des données sur N_r(d), affiché explicitement.

Règle de pointage V1 proposée, à afficher au professeur et à figer avec la référence :
- Pondération : diagnostic principal 2, justification principale 8, diagnostic alternatif 2, justification alternative 8, total 20.
- Un diagnostic obtient ses points si au moins un expert l’a retenu dans le même rôle ; sinon zéro.
- Pour une justification, les points bruts d’un choix sont le nombre d’experts ayant retenu cette donnée avec ce signe pour ce diagnostic dans ce rôle. R est leur somme pour les choix de l’étudiant.
- C est la somme des cinq plus grandes valeurs obtenues en retenant, pour chaque donnée disponible, le maximum des effectifs + et −. Justification = 8 × R / C.
- Si N_r(d) = 0, diagnostic et justification valent zéro, avec la mention « Hypothèse non représentée dans le panel pour ce rôle ». Si N_r(d) > 0 mais C = 0, bloquer la validation de la référence.
- Une donnée non sélectionnée rapporte zéro. Ne pas réduire C parce que l’étudiant a choisi moins de cinq données.
- Cette règle est une proposition pédagogique, pas une norme universelle des PRC. Ne pas qualifier automatiquement un choix non crédité d’erreur clinique.

Le professeur consulte les effectifs, peut ajouter une explication puis valide une référence immuable contenant copies sources, version du cas, calcul et pondérations. Une réponse étudiante ne modifie jamais cette référence.

Test chiffré : diagnostics crédités 2 + 2 ; justification principale R=6, C=10 ; alternative R=5, C=10. Résultat : 12,8/20, soit 64 %. Tester aussi les signes divergents et un diagnostic absent du panel dans un rôle.

## 6. Lancement étudiant et restitution minimale

« Lancer avec les étudiants » doit produire une vraie activité et afficher nom du PRC, statut, accès et commandes d’animation. Si une condition manque, afficher la cause et l’action nécessaire. Après ouverture des réponses, le participant rejoint réellement le cas et peut soumettre.

Le professeur voit les nombres de participants et de soumissions. Prévoir fermeture, révélation séparée des hypothèses principales, de leurs arguments, des alternatives, de leurs arguments et du corrigé, puis publication privée des notes. Des tableaux d’effectifs suffisent ici ; les graphiques élaborés sont différés.

Après publication, chaque étudiant voit uniquement sa copie, ses quatre composantes, ses signes et les effectifs pertinents du panel. Aucun classement individuel public.

Fermeture et soumission sont transactionnelles, avec heure serveur, contrôle de l’état et unicité d’une copie. Un double clic ne crée pas deux soumissions. Sauvegarde, fermeture, validation du corrigé et publication doivent survivre à un redémarrage. Les versions figées rendent chaque PRC réutilisable dans plusieurs groupes sans mélanger les résultats.

Limiter les requêtes : sauvegarde après modification avec debounce, actualisation professeur autour de cinq secondes uniquement pendant l’animation, actualisation d’état participant raisonnable autour de quinze secondes lorsque l’écran est visible. Ne pas recharger toutes les copies ou recalculer tout le panel à chaque requête. Le calcul d’un score relève de la soumission finale.

## 7. Livrer cette base puis s’arrêter à son périmètre

Accueil minimal : « Plan de raisonnement clinique (PRC) », connexion, rejoindre par code et « Ce logiciel a été créé par la Faculté de pharmacie de l’Université de Montréal. » Design universitaire sobre et lisible. Prévoir un petit jeu technique fictif isolé pour vérifier le circuit.

À différer à Codex : accueil interactif avec 20 observations, démonstration « Toux » complète avec dix experts et copies étudiantes, graphiques comparatifs aboutis, filtres avancés, annulation d’édition, prévisualisation enrichie, confort du mode animation et tests de charge à 300 étudiants. Ne pas ajouter de multi-PRC, de messagerie, d’IA clinique ou d’autre fonctionnalité dans cette étape.

Fournir :
- Code complet exportable vers GitHub, lockfile, commandes dev/build/typecheck/test, netlify.toml et migrations.
- .env.example avec uniquement des valeurs fictives : DATABASE_URL, APP_BASE_URL et variables d’initialisation de l’administrateur ; ajouter la connexion de migration ou d’autres secrets uniquement si nécessaires et documentés. Aucun secret sous un préfixe exposé au navigateur.
- README concis pour configuration et lancement ; HANDOFF.md décrivant architecture réelle, schéma, commandes, authentification, versions, routes, tests exécutés et éléments différés à Codex.
- Tests ciblés sur droits, pointage, absence de fuite, verrouillage et soumissions concurrentes ; essai complet avec professeur et participant dans des navigateurs distincts.

Critère de fin : un professeur crée et retrouve un PRC ; un panel répond ; le corrigé est généré et validé ; un étudiant rejoint, soumet et consulte son score après publication. Rapporter les vérifications réellement faites. Si les secrets Supabase manquent, terminer le code et les migrations, lister les valeurs à fournir et signaler les tests bloqués ; ne pas substituer une fausse base locale ou déclarer ces tests réussis.

Commence par un plan bref, puis construis uniquement cette base fonctionnelle et son passage de relais vers GitHub/Codex.
